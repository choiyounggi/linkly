# lnpl 0.2.0 프로덕션 준비도 최종 보고서

Wave 1 실측(4케이스, 커밋 713a4cb, 2026-08-05) 종합. 1차 소스는 4개 FINDINGS.md
(총 46건 F-기록)이며, 이 보고서의 모든 판정 문장은 F-번호 또는 evidence 경로를
인용한다. 46건 전건의 정규화 표·클러스터 배정·매트릭스 원자료는
`qa/report-appendix/friction-inventory.md`(이하 appendix)에 있다.

## 1. Executive Summary

**종합 판정: No-Go — lnpl 0.2.0은 플랫폼 전체로는 프로덕션 사용 불가.**
릴리스 게이트의 결과는 Ship / Ship-with-known-issues / Block 셋뿐이고, 수용자
없는 blocker가 스코프 안에 있으면 결과는 Block이다. 현재 미수용 blocker가 5건
있다. 단, 도메인 한정 **조건부 Go** 영역이 하나 존재한다: 요청-응답
CRUD·검증·이벤트 서비스 — t3 총평이 명시한 두 조건(CI에 stderr 진단 코드 게이트
부착 + 엔티티명 단일 단어 규약)을 known-issues로 문서화·수용하는 경우에 한한다
(상세는 §5).

세 줄 근거:

1. **미수용 blocker 5건, 전부 언어 안 우회 없음.** 가드 우변 필드 참조 불가로
   재고 초과 판매가 completed로 통과하고(t1 F-1, evidence/04 S2), 산술·할당
   부재로 재고 차감을 표현할 수 없으며(t1 F-2), 카드번호 원문이 result.bindings
   채널로 노출되고(t2 F-7 — "우회: 없음" 명기), 집계(sum/count)와 배치 트리거는
   어휘·문법 수준에서 표현 불가다(t3 F-1·F-2).
2. **"초록 파이프라인 ≠ 요구 충족" — 무음 실패 5개 클러스터(§4 C1~C5).** 4케이스
   중 3케이스(t1·t2·t3)가 9단계 전부 PASS인데 케이스 판정은 전부 "사용 불가"다:
   t2 총평은 "그 초록은 우회의 누적"이라 기록했고, t3 스코어카드는 "PASS는 표현
   가능한 부분집합이 파이프라인을 통과했다는 뜻이지 요구 충족이 아니다"를 판정
   규칙으로 명시했다. 0원 결제 승인(t2 F-2)·가드 skip의 completed 위장(t1 F-5,
   t2 F-6)·spec 블록 무음 병합(C1, 4/4 관측)이 모두 무증상으로 통과한다.
3. **예외 영역은 실측으로 확인됐다.** 가드 런타임은 3형태(when 비교식·when
   presence·until) 모두 mode A/B에서 실제 평가되고 무음 통과가 없었으며(t4 핵심
   측정 결과, evidence/04-modeA.md·05-modeB.md), 컴파일 진단·OpenAPI 문서 표면은
   높은 품질이다(t1 총평 "행과 토큰을 정확히 가리킨다"; t2 총평 "RFC 근거를
   명시하는 컴파일 진단"). 이것이 조건부 Go 영역의 근거다.

## 2. 실측 설계

**케이스 선정 논리.** 프로덕션 준비도를 구성하는 서로 다른 능력 축을 하나씩
겨냥해 4개 실전 케이스를 설계했다:

| 케이스 | 겨냥한 능력 축 | 소스 |
|--------|----------------|------|
| t1 inventory-order | 다중 엔티티 CRUD + 수량 비즈니스 규칙 + 상태 전이 | t1 FINDINGS 총평 |
| t2 payment-refund | 민감정보 마스킹·정책 선언·금액/기간 경계값 | t2 FINDINGS 헤더 |
| t3 batch-report | 집계·배치 트리거 — 어휘 한계의 의도적 프로브 | t3 FINDINGS 헤더 |
| t4 rate-notify | when/until 가드의 런타임 평가 실측 | t4 FINDINGS 헤더 |

**LLM-only 개발자 페르소나.** 각 세션은 "공개 문서만으로 개발하는 LLM 개발자"를
시뮬레이션했다: AGENTS.md 라우팅 + plugins/lnpl/skills/ 문서 + examples/ 샘플만
사용하고, 플랫폼 내부는 특성화 목적의 읽기만 허용(t1 FINDINGS 헤더). 이 규율의
이탈은 그 자체가 마찰 기록이다(t1 F-12; t4 측정 순도 캐비앗 — §7).

**측정 규율.** 플랫폼 수정 0건(t1 헤더 "수정 0건"; 브리프 out_of_scope). 공통
환경: 커밋 713a4cb, lnpl 0.2.0, python3.13 자체 venv, LLVM+SDK 경로,
`dev_doctor.sh` rc=0 (각 FINDINGS 환경 절, evidence/00-env.md). t3은 대조군
설계를 썼다: 공식 예제 examples/shorten.lnpl로 전 단계 PASS를 먼저 확인해
(t3 evidence/02-control-pipeline.md), 이후의 실패·제약이 환경이 아니라 케이스에
귀속됨을 증명했다.

## 3. 케이스별 스코어카드 종합

아래 매트릭스는 4개 원 스코어카드를 문자 그대로 전사한 것이다(검증: appendix와
동일한 셀 단위 대조 — 36셀 일치, t4 spec=FAIL 보존). **읽는 규칙: PASS는
"파이프라인 통과"이지 "요구 충족"이 아니다** — 요구 수준의 표현 가능성은
Frictions(§4)가 정본이다(t3 스코어카드 판정 규칙 원문: "Scorecard의 PASS는 '표현
가능한 부분집합이 파이프라인을 통과했다'는 뜻이지 요구 충족이 아니다").

| 단계 | t1 inventory-order | t2 payment-refund | t3 batch-report | t4 rate-notify |
|------|--------------------|--------------------|------------------|-----------------|
| authoring | PASS / 5 (.lnpl 수정→재실행 총계; 내역: 컴파일 3 + spec 2) | PASS / 편집 9회 (가드 3·엔티티 2·spec 4) | PASS (부분집합 — 요구 3개 중 (c)만 온전, (a) 잔여부, (b) 표현 불가) / 9 (프로브 a 공통 4 + a3 3 + spec 2) | PASS / 3 (emit 이름 1 + spec 재구성 2) |
| parse | PASS / 0 | PASS / 8 (에러 3·성공 5) | PASS / 0 (최종본 기준) | PASS / 0 (첫 컴파일 rc=0, 의도된 경고 1) |
| lower | PASS / 0 | PASS (24 nodes) / 8 (parse와 동일 명령) | PASS (compile이 parse+lower 일체 수행, IR 생성) / 0 | PASS / 0 |
| validate | PASS / 0 | PASS / 4 (재컴파일마다 재검증, 전부 PASS) | PASS / 0 | PASS / 0 |
| modeA | PASS / 0 (변형 6회 전부 구동; 의미 갭은 F-1·F-5·F-6) | PASS / 워크플로당 2 (+경계 프로브 6실행) | PASS (BuildReport·GetReport 각 completed) / 1 (워크플로 id 표기 — F-7) | PASS / 1 (F-2로 1차 6/7 실패 → 수정 후 7/7 rc=0) |
| modeB | PASS / 1 (`--field` 키 형식 규명) | PASS / 1 | PASS / 0 | PASS / 1 (F-3로 1차 전 런 오평가 → dotted 재실행) |
| differential | PASS / 0 (EQUIVALENT 4/4) | PASS (EQUIVALENT 4/4 ×2 워크플로) / 1 | PASS (두 워크플로 모두 4/4 EQUIVALENT) / 0 | PASS / 0 (r1·r2 모두 EQUIVALENT 4/4) |
| openapi | PASS / 0 | PASS / 1 | PASS / 0 | PASS / 0 |
| spec | PASS / 2 (3케이스→1케이스 축소 — F-7) | PASS (4 passed, 0 failed) / 6 | PASS (7 passed, 0 failed — 정상 1·에러 1·경계 1) / 2 (복수 케이스 병합 — F-5) | **FAIL** / 3 (상한 도달 — F-4·F-5·F-7) |

36셀 중 유일한 FAIL은 **t4 spec**(재시도 상한 3회 도달 — t4 F-4·F-5·F-7)이다.
t1·t2·t3의 spec PASS도 원형 요구의 통과가 아니다: 셋 다 "정상+에러+경계 3케이스"
요구를 1케이스 축소(t1 F-7)·2워크플로 분산(t2 F-10)·경계 전용 워크플로 추가
(t3 F-5)로 우회한 뒤의 초록이다.

**재시도 수 각주**: 계수 규칙이 케이스별로 다르다(t1 "수정→재실행 총계", t2
"편집 횟수·명령 재실행", t3 "프로브 시도", t4 "attempt 수"). 케이스 간 합산·비교는
무효이며, 수치는 각 케이스 안의 방향성 신호로만 읽는다(appendix §3 각주).

## 4. 교차 마찰 분석

46건 F-기록을 근본 원인으로 묶으면 10개 클러스터가 나온다(배정 전건은 appendix
§1~§2; F 1건당 주 클러스터 1개). 심각도는 구성원 최고값을 그대로 쓰고 인상하지
않았다 — 반복 관측 횟수는 심각도가 아니라 우선순위(§6)의 근거다.

### 무음 실패 계열 — 파싱·컴파일은 초록인데 의미가 조용히 증발한다

**C1. spec 블록 무음 병합 — 워크플로당 1케이스 강제** · major · **4/4 케이스 관측**
— t1 F-7, t2 F-10, t3 F-5, t4 F-4. 워크플로 하나에 spec 블록 여러 개를 선언하면
무경고로 한 케이스로 병합돼 given이 뒤섞이고 expect에 completed와 failed가
공존한다(t1 evidence/08 manifest 원문; t3 재현: manifest에 "케이스 1개" 실측).
귀결: 테스트 최소셋(정상+에러+경계)을 언어 안에 실을 방법이 없다. 4개 세션이
서로 독립적으로 같은 벽에 부딪혔으므로 개별 마찰이 아니라 **플랫폼 결함**으로
명명한다.

**C2. 가드 skip = completed·rc=0 — 거부 의미론 부재** · major · 3/4 관측 —
t1 F-5, t2 F-6, t4 F-9. 가드가 false면 스텝이 스킵되는데 워크플로는 성공으로
종료한다: 재고 부족 주문이 "성공"(t1 evidence/04 S3), 한도 초과 결제 거절과 승인
성공이 최상위 신호로 구별 불가(t2 evidence/raw/run-approval-amt1000001.out).
until 0라운드는 skipped 목록에도 안 남아 when 스킵과 비대칭이다(t4 F-9).

**C3. 선언·참조의 무음 증발/지연 실패** · major · 3/4 관측 — t2 F-2, t3 F-3·F-8,
t4 F-2. 연쇄 when 가드의 첫 번째가 무진단으로 IR에서 탈락해 0원·음수 결제가
승인되고(t2 F-2, T05 런타임 증명), unknown-verb 스텝은 exit 0으로 "성공한 척"
완주하며(t3 F-3 — 진단은 stderr 전용), 미선언 이벤트 참조는 compile·validate를
통과해 런타임에만 실패하는데 가드가 그 스텝을 스킵하면 rc=0으로 프로덕션까지
잠복한다(t4 F-2). 경고를 기계적으로 잡을 종료 코드 채널이 없다(t3 F-8).

**C4. `--field` 이름 불일치 무경고 무시** · major · 2/4 관측 — t1 F-9, t4 F-3.
mode B에서 잘못된 필드 키는 무경고로 무시되고 기본값 0으로 가드가 평가된다 —
5개 런이 사실상 동일 거동이 될 때까지 아무 신호가 없다(t4 evidence/05-modeB.md).

**C5. 출력 채널 간 집행 불일치 — 마스킹 누수·계약 과대 광고** · **blocker** ·
2/4 관측 — t2 F-7·F-8·F-9, t1 F-6. Password 타입 마스킹이 trace 채널에는
적용되고(`***`) result.bindings 채널에는 적용되지 않아 카드번호 원문이 응답에
실린다(t2 F-7, evidence/04-modeA-masking.md — 우회 없음). 생성된 OpenAPI는
`writeOnly`로 "응답 미출현"을 약속해 문서가 런타임보다 안전을 과대 광고하고
(t2 F-8), differential의 "masking PASS"는 누수 채널을 비교 표면에 포함하지
않는다(t2 F-9). 같은 구조로, 선언된 refinement facet(min=1)이 런타임에서
미집행돼 qty=0 주문이 통과하는데 OpenAPI 400 서술과 어긋난다(t1 F-6,
evidence/04 S4·evidence/07).

### 표현력 공백 계열 — 언어 안에 우회가 없는 표현 불가

**C6. 값 의미론 부재 — 산술·할당·집계·파생값·상태 전이·동사 어휘 폐쇄** ·
**blocker** · 4/4 관측(t2는 F-5의 산술 측면 교차 관측) — t1 F-2·F-3, t3 F-1,
t4 F-1. 재고 차감(stock - quantity)을 표현할 산술·할당 문법이 없고(t1 F-2),
sum/count 집계는 어휘·문법 양쪽에서 부재하며(t3 F-1 — VERB_LEXICON 16개 전부
I/O 계열, 공식 예제 checkout조차 total을 "서술(계산 안 됨)"로 자인), 상태 전이
규칙은 enum 타입 선언까지만 가능하고(t1 F-3), notify/send 동사가 없어 "발송"이
기록+이벤트로 근사된다(t4 F-1).

**C7. 가드 조건 표현력 한계** · **blocker** · 3/4 관측 — t1 F-1, t2 F-1·F-3·F-4,
t4 F-7. 가드 우변은 리터럴만 허용돼 `product.stock >= order.quantity`가 컴파일
거부되고(t1 F-1 — 귀결: S2 재고 초과 판매 completed), 가드는 read된 저장 행만
참조할 수 있어 입력값 검증이 표현 불가이며(t2 F-1), AND 결합·등가(==)가 없어
범위·전액 환불 검증이 축소되고(t2 F-3), Money 필드 가드는 컴파일을 통과한 뒤
런타임 raw traceback으로 크래시한다(t2 F-4). RFC-0008이 약속한 `==`/`!=`는
생성된 grammar.md에 없다(t4 F-7).

**C8. 시간·기간·스케줄 정책 공백** · **blocker** · 2/4 관측 — t2 F-5, t3 F-2.
"결제 후 30일 이내" 시간창은 DateTime 산술·비교 불가로 표현할 수 없고 — 사전
계산 `ageDays` 필드 우회는 나이 갱신 책임을 플랫폼 밖으로 전가한다(t2 F-5).
"매일 자정 실행" 배치 트리거는 동사·선언·제어 어휘 어디에도 없다(t3 F-2).

**C9. spec given 의미론 결함** · major · 3/4 관측 — t1 F-8, t2 F-11·F-12,
t4 F-5·F-6·F-12. given은 기본 payload에 병합되지 않고 통째 대체돼 경계값
시나리오가 불가하고(t2 F-11), 러너가 given의 id를 payload에 적용하지 못해 run이
실행하는 payload를 spec은 실행하지 못하며(t4 F-5), `stored`는 소문자만 받으면서
선언된 엔티티를 "not a declared entity"로 보고한다(t1 F-8, t2 F-12). 실패 시
사유도 출력되지 않는다(t4 F-12). C1과 결합하면 spec 검증 경로는 사실상 사용
불가다(t4 총평).

### 문서·진단 계열

**C10. 미문서 규칙·문서-구현 불일치** · major · **4/4 케이스 관측** — t1 F-4·F-12,
t2 F-14, t3 F-4·F-6·F-7, t4 F-8·F-11. 가드 스코프(다음 1스텝만 — t1 F-4), 다단어
엔티티 참조 불가(에러 지시를 따라도 실패 — t3 F-4), 복수형 명사 불인식(t3 F-6),
`--workflow`의 IR id 요구(t3 F-7), RFC가 약속한 guarded 예제 부재(t4 F-8), CLI
플래그 커버리지 갭(t1 F-12), KB 보안 질의 오라우팅(t2 F-14)이 전부 미문서
규칙이라 재시도를 불렸다 — t3 authoring 재시도 9회의 주 원인이 F-4다.

**클러스터 미배정(단독 관찰)**: t1 F-10(payload 평평 병합)·F-11(결정론 실패에도
retry), t2 F-13(전체 필드 강제 제출), t4 F-10(rows 신호 부재) — appendix §1 참조.

DoD 대조: ≥3케이스에서 반복 관측된 클러스터는 C1(4/4)·C10(4/4)·C6(4/4, 교차
1건 포함)·C2·C3·C7·C9(각 3/4)로 **7개** — 요구치(최소 3개, spec 무음 병합 포함)를
충족한다.

## 6. 선결 과제 우선순위

impact 순. 순서 논리는 우선순위 요인(business exposure > reach·frequency >
workaround cost)이다 — 심각도는 원 기록의 사실 축 그대로 두고, 순서는 별도
축으로 매겼다.

| # | 과제 | 해소하는 F | 순서 논리 |
|---|------|-----------|-----------|
| 1 | 마스킹 집행 채널 통일(result.bindings 포함 전 채널) + differential 비교 표면에 누수 채널 포함 | t2 F-7·F-8·F-9 | business exposure: 유일한 보안 누출 blocker, 언어 안 우회 없음 |
| 2 | 거부/실패 의미론 — 가드 skip을 status·rc로 관측 가능하게(until 0라운드 비대칭 포함) | t1 F-5, t2 F-6, t4 F-9 | reach: 가드 쓰는 모든 워크플로에서 정책 위반이 무증상 |
| 3 | 무음 증발의 컴파일 타임 이동 — 연쇄 가드 탈락 진단, 미선언 이벤트 참조 거부, `--strict`/exit 게이트, `--field` 오키 경고 | t2 F-2, t3 F-3·F-8, t4 F-2·F-3, t1 F-9 | frequency: 4/4 케이스가 무음 함정에 걸림(C3·C4) |
| 4 | spec 러너 수리 — 블록별 독립 케이스, given 대체→필드 머지, id 적용, 실패 사유 출력 | t1 F-7·F-8, t2 F-10·F-11·F-12, t3 F-5, t4 F-4·F-5·F-6·F-12 | reach: C1은 4/4 관측 — 테스트 최소셋을 언어 안에서 원천 봉쇄 |

## 7. 측정의 한계

1. **t4 측정 순도 캐비앗(원 기록 인용).** t4 세션은 계획 단계에서 허용 문서 외에
   `impl/lnpl/cli.py`·`repo_policy.py`·`interp.py`·`examples/*.lir.json` 등을
   열람했다고 자기 기록했다 — 해당 항목의 "발견 난이도" 측정은 오염(선확인)이며,
   어휘·문법 마찰과 실행 결과 측정은 유효하다(t4 "측정 순도 캐비앗" 절). 또한
   브리프가 인용한 "RFC-0008 G8" 식별자가 RFC에 존재하지 않아 §2·§3.1로 매핑해
   측정했다(같은 절).
2. **페르소나 이탈이 강제된 지점.** t1도 CLI 표면의 문서 커버리지 갭 때문에
   `impl/lnpl/cli.py`를 직접 읽어야 했다(t1 F-12 — "실전 SaaS 상황이면 불가능한
   우회"). "공개 문서만" 시뮬레이션은 이 지점들에서 순도가 깨졌고, 그 깨짐 자체가
   F-기록이다.
3. **표본 크기.** 4케이스·단일 커밋(713a4cb)·케이스당 1세션이다. 도메인 커버리지는
   설계로 분산했지만(§2), 같은 케이스를 다른 세션이 반복했을 때의 분산은 측정하지
   않았다.
4. **단일 페르소나.** 모든 세션이 같은 "LLM-only 개발자" 페르소나다. 사람 개발자,
   또는 내부 소스를 자유 열람하는 개발자의 마찰 프로파일은 다를 수 있고 이번
   측정의 범위 밖이다.
5. **미측정 축.** 성능·동시성·장기 운영·실 부하는 측정하지 않았다. 이 보고서의
   판정은 기능·표현력·관측성 축에 한정된다.
6. **측정 자체의 컨트롤.** 점수는 컨트롤과 함께 공표해야 신뢰할 수 있다 — 이번
   측정에서 그 역할은 t3의 대조군이다: 공식 예제 shorten.lnpl이 동일 환경에서
   전 단계 PASS였으므로(t3 evidence/02-control-pipeline.md), 본 보고서의 실패·
   제약 기록은 환경 문제가 아니라 케이스(플랫폼 표현력·관측성)에 귀속된다.
