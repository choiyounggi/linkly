# 07-schedule-trigger — R2, C5

`event DailyRollup on schedule daily at 02:00 UTC` (src/settlement.lnpl:33), owned by
`service RollupService` → `workflow ComputeDailyRollup` (the service's sole workflow, so
the "exactly one workflow child" connection rule for `--schedule` resolves unambiguously —
confirmed by `lnpl trigger` succeeding below without an ambiguity error).

## Compile-time classification
`declared-not-enforced` info diagnostic at compile (see `02-compile.md`) — matches
`docs/ENFORCEMENT-MATRIX.md` line 83 verbatim: the schedule declaration itself calls
nothing; only an external scheduler hitting `lnpl trigger --schedule <id>` or
`POST /-/schedules/<slug>` (`lnpl serve`) runs the linked workflow.

```
$ lnpl schedules src/domain.lnpl src/settlement.lnpl --format crontab
# generated by `lnpl schedules` from src/domain.lnpl, src/settlement.lnpl — do not

# DailyRollup: daily at 02:00 UTC (assumes the cron daemon's clock is UTC)
0 2 * * * lnpl trigger src/domain.lnpl src/settlement.lnpl --schedule event.daily.rollup
```

## C5 — trigger for 2026-07-15 (small fixture uses 2026-07-01 for this smoke test; C5's
10k-store, 2026-07-15 run was not executed — see FINDINGS coverage table)
```
$ lnpl trigger src/domain.lnpl src/settlement.lnpl --schedule event.daily.rollup \
    --backend sqlite:.claude/tmp/s3/small.db \
    --payload '{"id":"dailytotal-M1-2026-07-01","merchant":"M1","status":"settled","dayKey":"2026-07-01"}'
```
rc=0, `workflow ComputeDailyRollup -> completed`, `gross={"amount":"10.00","currency":"USD"}`
(M1's one settled tx that day = $10.00), `count=1`. Note: **`lnpl trigger` has no `--json`
flag** (unlike `run`/`spec`) — `cli-surface.md`'s own trigger flag table already says so;
confirmed by trying it (`unrecognized arguments: --json`), so this cost 0 extra rounds once
the table was actually consulted before typing the command.

**Row-key caveat (own finding, not in docs read):** without an explicit `id` in the
payload, `create dailytotal as newDailyTotal`'s row key falls back to `<entity_id>#-`
(per `lnpl-authoring/references/spec.md`'s "`(엔티티, 키)`" rule) — a *first* trigger
without `id` for M1 landed at row key `entity.daily.total#-`. **Every merchant on every
day would collide at that same key** unless the caller supplies a unique `id` per
(merchant, day) — the language gives no default disambiguation. Re-ran with an explicit
`id: "dailytotal-M1-2026-07-01"` for the result quoted above.

## Second trigger, same day (re-run safety)
```
$ lnpl trigger ... --payload <same payload, same id>
workflow ComputeDailyRollup -> failed
  step create dailytotal as newDailyTotal   ERROR step failed
```
Fails closed (`create` conflicts on the same key) — no double-count, no silent overwrite.
Same "skip via failure, not upsert" shape as `MonthlySettlement` (see `08-rerun-oracle.md`
for the analogous R5 case and why an in-language *update* isn't available for a Money-
bearing row).

## Enforcement classification
`event ... on schedule` itself does nothing at runtime (confirmed: no cron/timer registers
itself; `declared-not-enforced` is accurate). `lnpl trigger --schedule <id>` **does** run
the linked workflow correctly when called, and refuses to run it a second time for the same
key. Wiring the daily 02:00 cadence to an actual clock is entirely the external scheduler's
job (`lnpl schedules`' own output line 1 says so) — this is unchanged from `docs/serving.md`
and not itself a friction, just confirmed by execution rather than assumed from the doc.
