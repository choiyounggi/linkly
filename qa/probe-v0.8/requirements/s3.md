# S3 — 월간 가맹점 정산 배치·집계·리포트

**역할**: 당신은 결제 대행사의 정산 팀 개발자다. 이전 감사에서 "배치·집계 워크로드는
Block"이었다. v0.8.0의 RowSet·group by·avg/min/max·Money·on schedule·trigger로 그 판정을
뒤집을 수 있는지 시험한다.

## 도메인

- `Merchant`(id, name, tier ∈ {small, large})
- `Transaction`(id, merchant, amount(USD 센트), fee(센트), status ∈ {settled, refunded, pending}, occurred_at)
- `DailyTotal`(merchant, day, gross, count)
- `Settlement`(merchant, month, gross, fees, net, tx_count, avg_ticket, max_ticket, min_ticket, status)

## 요구사항

| R | 요구 |
|---|------|
| R1 | **시드**: Transaction **10,000행**(가맹점 50개, 3개월, status 분포 settled 90% / refunded 5% / pending 5%)을 만든다. 시드 생성 도구는 lnpl 밖(파이썬 스크립트)이어도 되지만 저장은 lnpl이 읽는 저장소(sqlite 또는 postgres)에 해야 한다. 시드 방법과 소요 시간 기록. |
| R2 | **일별 집계 잡** `daily_rollup`: 매일 02:00에 전날 settled 거래를 가맹점별로 gross=sum(amount), count=count()로 `DailyTotal`에 쓴다. `on schedule` 선언 + 외부 스케줄러가 부를 `lnpl trigger` 경로로 실행. 스케줄 스니펫(`lnpl schedules`) 생성. |
| R3 | **월간 정산** `monthly_settlement(month)`: 가맹점별로 해당 월 settled 거래만 — gross=sum(amount), fees=sum(fee), net=gross−fees, tx_count=count, avg_ticket=avg(amount), max/min_ticket. `refunded`·`pending`은 제외. 결과를 `Settlement`에 저장. |
| R4 | **등급 수수료 규칙**: tx_count > 1000이면 fees를 gross의 1.5%로 재계산, 아니면 저장된 fee 합계 그대로. Money 산술로. |
| R5 | **멱등 재실행**: 같은 달을 두 번 돌려도 Settlement는 가맹점당 1행, 값 동일. 두 번째 실행이 갱신인지 skip인지 기록. |
| R6 | **정합 검증**: 파이썬으로 같은 집계를 독립 계산해 lnpl 결과와 **전 가맹점 전 필드** 비교. 불일치 0건이어야 한다. avg의 반올림 규칙 기록. |
| R7 | **성능**: 10k 행 월간 정산 벽시계 시간(모드 A). 1k·10k에서 측정해 선형인지 기록. 드라이버 pushdown이 있으면 켜고 끄고 비교. 100k는 시도만(10분 넘으면 중단·기록). |
| R8 | **리포트 API** `GET /settlements/{month}`: 가맹점별 정산 목록 + 상단 합계(전체 gross·net·가맹점 수). 정렬 net 내림차순, 상위 10개만. |
| R9 | **백필**: 요구사항 변경 — `Transaction`에 `currency` 필드 추가(기본 "USD"). 기존 10k 행에 `lnpl migrate`(또는 동등)로 백필. 소요 시간·중간 실패 시 재개 가능 여부. |
| R10 | **spec**: R3·R4·R5를 소규모 시드(가맹점 2개, 거래 6건)로 spec에 표현해 통과. 집계 결과 필드값 단언이 가능한지 기록. |

## 기록 요령

- 집계 표현이 언어에 없어서 파이썬으로 우회했다면 **어느 부분**이 우회인지 정확히(전체 집계? 등급 규칙? 정렬?). 우회 비율이 이 케이스 판정의 핵심이다.
- 성능은 `time` 출력 원문. 프로파일 수단이 있으면(예: `--log-level`, 트레이스) 어느 단계가 지배적인지.
- `on schedule` 선언이 실행기에서 실제로 무엇을 하는지(unenforced인지 trigger로 연결되는지) 문서·실행 출력으로.
