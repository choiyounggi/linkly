# S4 — 운영 배포: 실드라이버·경화·마이그레이션·부하·드레인

**역할**: 당신은 SRE다. 개발팀이 넘긴 lnpl 서비스를 **프로덕션 형태**로 띄우고 운영 절차를
검증한다. 서비스 자체는 작게 — `examples/linkhub.lnpl`을 그대로 쓰거나, 엔티티 2~3개짜리
"짧은 URL + 조회 카운트" 서비스를 새로 쓴다(authoring은 이 케이스의 관심사가 아니다;
30분 넘게 걸리면 linkhub로 간다). 관심사는 아래 운영 요구다.

## 요구사항

| R | 요구 |
|---|------|
| R1 | **postgres 실바인딩**: Docker로 postgres 16을 띄우고 `lnpl-postgres` 드라이버로 서비스한다. 스키마가 어떻게 만들어지는지(자동/수동), `lnpl db` 검사 출력. |
| R2 | **redis 실바인딩**: Docker redis 7 + `lnpl-redis`. 어떤 워크플로가 캐시를 쓰는지 선언하고, 캐시 히트가 실제로 일어남을 redis MONITOR 또는 INFO로 증명. |
| R3 | **OTel 실수신**: Docker otel-collector + `lnpl-otel`. 요청 1건이 collector 로그에 span으로 도착. `service.name`·trace id 전파(`--trust-incoming-trace`) 확인. |
| R4 | **경화 옵션 일괄**: `--rate-limit`, `--grace-period`, `--metrics`, `--jwt-secret-env`+`--jwt-issuer`, `--log-format`(JSON), `--host 0.0.0.0`. 각각 실제 동작을 curl로 증명(429, /-/metrics 스크랩, 401, JSON 로그 1줄). |
| R5 | **설정 프로파일**: `lnpl.toml`에 dev(fake)/prod(postgres+redis+otel) 프로파일. 같은 소스가 `--profile dev`·`--profile prod`로 뜨고, 비밀은 env로만(토ml에 평문 비밀 0). |
| R6 | **Docker 이미지**: 서비스 이미지를 빌드(`examples/deploy/Dockerfile` 참고 가능)해 compose로 postgres·redis·collector와 함께 뜬다. 이미지 크기·빌드 시간·비-editable 설치에서 `lnpl serve`가 도는지. |
| R7 | **부하**: 100 rps × 60초(도구 자유: `hey`/`wrk`/파이썬 스크립트) — p50/p95/p99 지연, 오류율, 프로세스 RSS. fake 백엔드 vs postgres 백엔드 둘 다. |
| R8 | **드레인**: 부하 중 `SIGTERM` → 진행 중 요청은 완료되고 새 요청은 거부, 손실 0. `--grace-period` 값별 동작. |
| R9 | **스키마 변경 무중단**: 엔티티에 필드 1개 추가 → 백업(`docs/backends.md` §14) → `lnpl migrate` 백필 → 새 버전 배포. 구버전 프로세스가 도는 동안 신버전이 뜨는지(expand-contract), 복원 절차가 실제로 돌아가는지. |
| R10 | **헬스·준비**: liveness/readiness 엔드포인트가 있는지, postgres가 죽었을 때 readiness가 실패로 바뀌는지, 복구 시 자동 회복하는지. |

## 시나리오

| D | 조건 | 기대 |
|---|------|------|
| D1 | prod 프로파일 기동 | 3개 드라이버 전부 실연결 로그, `lnpl db` 정상 |
| D2 | 200 req 버스트 (rate-limit 50/s) | 429 비율 관측, 메트릭에 반영 |
| D3 | 100 rps 60s fake vs postgres | 두 p99 값, 오류율 |
| D4 | 부하 중 SIGTERM | 손실 0, 종료 시간 ≤ grace |
| D5 | postgres 컨테이너 stop → start | readiness 실패 → 회복, 서비스 프로세스 생존 |
| D6 | 필드 추가 + migrate + 롤백(복원) | 데이터 손실 0, 소요 시간 |

## 기록 요령

- 드라이버 설치·연결에 걸린 라운드와 문서 어느 줄을 따랐는지(외부 레포 README 포함).
- "안 되는 것"은 Block 판정 근거가 되므로, 없는 기능(예: readiness 부재)은 우회하지 말고 없다고 기록 후 어떤 형태로 있어야 하는지 제안.
- Docker 컨테이너·볼륨은 케이스 끝에 정리(`docker compose down -v`). 정리 명령도 evidence에.
