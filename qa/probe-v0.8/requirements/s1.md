# S1 — OrderHub: 다중 팀 주문·재고·결제 서비스

**역할**: 당신은 전자상거래 회사의 백엔드 팀 리드다. 세 팀(catalog · orders · payments)이
한 코드베이스에서 일한다. 아래 요구사항을 **lnpl 0.8.0만으로** 구현하고 REST로 서비스한다.
s5 워커가 같은 문서를 FastAPI로 구현하므로 요구사항을 재해석하지 말 것.

## 도메인

- **catalog 팀**: `Product`(sku, name, price(통화 USD, 센트 단위 정밀), kind ∈ {physical, digital}, active), `Category`
- **orders 팀**: `Customer`(id, tier ∈ {standard, vip}, email), `Order`(id, customer, status, subtotal, discount, tax, total, created_at), `OrderLine`(order, product, qty, unit_price, line_total), `StockReservation`(product, order, qty)
- **inventory (orders 팀 내부)**: `Stock`(product, on_hand) — **orders 팀 밖에서 보이면 안 되는 내부 선언**
- **payments 팀**: `Payment`(order, amount, card_last4, status), `Refund`(payment, amount, reason)

## 요구사항

| R | 요구 |
|---|------|
| R1 | **코드베이스 구조**: 팀별로 소스가 분리되고(디렉터리 또는 파일 3개 이상) 한 번에 컴파일·실행된다. `Stock`은 orders 팀 밖에서 참조하면 컴파일이 거부돼야 한다. |
| R2 | **주문 생성** `POST /orders`: 라인 1개 이상. 각 라인은 `Stock.on_hand >= qty`여야 하며 성공 시 그만큼 `StockReservation`을 만들고 on_hand를 차감한다. 재고 부족이면 주문 전체 거부(부분 예약 잔존 금지). |
| R3 | **금액 계산**: subtotal = Σ(qty × unit_price). vip이면 discount = subtotal의 10%. tax = (subtotal − discount)의 8%. total = subtotal − discount + tax. 전부 센트 정수 정밀도, 반올림 규칙은 문서화한 것을 따르고 evidence에 실제 값을 남긴다(예: 3 × $19.99 vip). |
| R4 | **상태 전이**: `pending → paid → shipped → delivered`. `cancelled`는 pending·paid에서만. 그 외 전이(예: shipped → cancelled, delivered → paid)는 거부되고 상태가 바뀌지 않는다. |
| R5 | **결제** `POST /orders/{id}/pay`: amount == total이어야 함. 카드 번호는 입력받되 저장·로그·응답 어디에도 원문이 남지 않고 last4만 남는다. 결제 실패(입력의 `simulate_failure: true`)면 Payment가 남지 않고 주문은 pending 유지, 예약은 유지. |
| R6 | **취소** `POST /orders/{id}/cancel`: paid 상태 취소 시 환불(Refund) 생성 + 예약 해제(on_hand 복원)가 **둘 다** 일어나거나 둘 다 안 일어나야 한다(중간 실패 시 부분 반영 금지 — 어떻게 보장하는지 evidence). |
| R7 | **환불** `POST /payments/{id}/refund`: 부분 환불 허용, 누적 환불액 ≤ 결제액. 한 결제에 환불은 최대 3회. `admin` 역할만 호출 가능(그 외 403 또는 동등한 거부). |
| R8 | **API 문서**: OpenAPI 3.1 문서를 생성하고, 실제 서버(`lnpl serve`)에 curl로 A1~A8을 쳐서 응답 코드·본문을 evidence에 남긴다. |
| R9 | **수용 시나리오 A1~A8을 spec으로** 작성해 전부 통과시킨다(아래 표). 각 A는 최소 1개 저장소 단언(행 수 또는 필드값)을 포함한다. |
| R10 | **변경 요청**(모든 것이 끝난 뒤): "주문 라인에 `gift_wrap` 옵션 추가, 라인당 $2.00 가산, `digital` 상품엔 불가(거부)." 반영 diff 크기·라운드·기존 spec 중 깨진 것을 METRICS에 기록. |

## 수용 시나리오 (s5와 공통 — 이름·입력·기대를 바꾸지 말 것)

시드: Product `P1` physical $19.99 on_hand 5, `P2` digital $9.99 on_hand 999, `P3` physical $5.00 on_hand 0. Customer `C1` standard, `C2` vip.

| A | 시나리오 | 입력 | 기대 |
|---|----------|------|------|
| A1 | 표준 주문 | C1, P1×2 | 201, subtotal 3998, discount 0, tax 320, total 4318; Stock P1 on_hand 3; Reservation 1행 |
| A2 | vip 할인 | C2, P1×3 | subtotal 5997, discount 600(반올림 규칙 명시), tax 432, total 5829 |
| A3 | 재고 부족 | C1, P1×2 + P3×1 | 거부(4xx 또는 동등), Reservation 0행, P1 on_hand 5 유지 |
| A4 | 결제 성공 | A1 주문에 amount 4318, card 4242424242424242 | Payment 1행 status captured, card_last4 "4242", 응답·저장에 "4242424242424242" 부재; Order paid |
| A5 | 금액 불일치 결제 | A1 주문에 amount 100 | 거부, Payment 0행, Order pending |
| A6 | 불법 전이 | A4 주문을 shipped 후 cancel | 거부, Order shipped 유지 |
| A7 | paid 취소 원자성 | A4 주문(shipped 전) cancel | Order cancelled, Refund 1행 amount 4318, P1 on_hand 5 |
| A8 | 환불 한도 | A4 결제에 refund 2000 ×2 후 refund 1000 | 3번째 거부(누적 5000 > 4318), Refund 2행; admin 아닌 호출자는 첫 시도부터 거부 |

## 기록 요령

- R1의 가시성 거부는 **실제로 위반 코드를 써서** 컴파일 거부를 evidence로 남긴다.
- R3의 반올림: 600 = 5997 × 0.10 = 599.7 → 문서가 정한 규칙(반올림/내림)과 실제 값을 함께 기록. 기대값 표의 tax는 (5997−600)×0.08 = 431.76 → 432 로 계산했다. 플랫폼이 다른 규칙을 쓰면 그 값을 기록하고 F-항목으로.
- R6의 원자성은 "실패를 주입"해서 증명한다(예: Refund 생성 뒤 예약 해제 단계에 가드가 걸리는 입력). 주입할 방법이 없으면 그 사실이 F-항목이다.
