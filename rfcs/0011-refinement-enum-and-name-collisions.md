# RFC-0011: Refinement enum 정합과 이름 충돌

## Status

- Status: **Accepted** (RFC-0011, 2026-08-05)
- Updates: RFC-0001 §부록 A.6.3, RFC-0001 §부록 A.7

## Motivation

RFC-0001 부록 A.6이 refinement의 직렬화를 규정한 뒤(2026-08-04), 참조 구현에서
**어느 층도 거부하지 않지만 아무 값도 받을 수 없는 refinement**를 작성할 수 있음이
드러났다. 2026-08-05 실측:

```
refine Tier of Integer
    enum bronze silver
```

이 소스는 컴파일되고, OpenAPI로
`{"type":"integer","format":"int64","enum":["bronze","silver"]}` 를 생성한다.
정수이면서 문자열 `"bronze"` 와 같은 값은 존재하지 않으므로 이 스키마는
**충족 불가능(unsatisfiable)** 하다. 런타임도 같다 — 정수 값은 enum 멤버십에서
탈락하고 문자열 값은 base `Integer` 검사에서 탈락한다. 층들은 서로 모순되지
않으며 잘못된 값이 통과하지도 않는다. 유일한 피해는 **작성자가 진단을 받지
못한다는 것**이다: 결코 무엇도 받아들일 수 없는 타입을 선언해 놓고 오류를 보지
못한 채 다음 단계로 간다.

원인은 구현이 아니라 명세의 공백이다. 부록 A.6.3의 `enum` 행은 값 형식을
"배열(문자열 또는 수치)"로 적고 적용 범주를 "텍스트류 · 수치류"로 적을 뿐,
**항목의 형이 base와 맞아야 한다는 요구를 어디에도 두지 않는다.** 그 공백이
`Integer` base에 문자열 항목을, `Text` base에 수치 항목을 허용한다.

이 갱신은 그 요구를 A.6.3에 규범으로 추가한다. 컴파일 패스는 위반 시 오류를
일으켜야 한다(A.7의 구분에 따라 이는 문서 수준 불변식이며 스키마가 아니라
패스가 소유한다).

### 두 번째 결함 — Entity와 Refinement의 이름 충돌

같은 날 실측한 두 번째 사례다:

```
refine Link of Text
    maxLength 8
entity Link
    field
        code Text
```

이 소스도 컴파일되고, 이름이 `Link` 인 노드 **둘**(`Refinement`, `Entity`)을
내보낸다. 두 노드는 OpenAPI 투영에서 `components/schemas` 의 **같은 키**로
들어가므로 한쪽이 다른 쪽을 덮어쓴다. 참조 구현은 생성 단계에서
`OpenApiError` 로 이를 막고 있으나, 이는 **마지막 방어선**이다 — 컴파일이
통과시킨 문서가 생성기까지 가서야 거부되므로, IR 소비자 중 생성기를 거치지
않는 쪽(런타임·에이전트)은 두 `Link` 를 그대로 본다.

원인은 A.7 불변식 ⓔ가 충돌 대상으로 18종 base·preset·타 `Refinement` 만
열거하고 **같은 문서의 Entity 이름을 빠뜨린 것**이다. 이 갱신은 ⓔ에 Entity
이름을 추가한다.

### 개정 관계

RFC-0007 §2.2의 **Updates** 관계다. RFC-0001은 `Accepted`이고 두 변경 모두
실질 변경이므로 — A.6.3은 이미 서술된 규칙을 **좁히고**(현재 문언은
`refine Kind of Text` + `enum draft 1 2.5` 를 허용하며 커밋된 테스트가 이를
고정하고 있었다), A.7 ⓔ는 이미 서술된 불변식을 **넓힌다** — §2.1에 따라 본문
편집이 아니라 절 단위 갱신으로 처리한다. 지목한 절은 §부록 A.6.3 과 §부록 A.7
둘이며, 지목하지 않은 절(A.6.1·A.6.2·A.6.4·A.6.5·A.6.6)과 모순되지 않는다.

**치환 시 원문과 달라진 곳 5건** (A.6.3에 2건, A.7에 3건)**.** RFC-0007 §2.2
규칙 4가 "치환 후의 최종 텍스트"를 요구하므로, 아래 두 절은 원문을 그대로 옮기되
다음만 다르다. 이 다섯 외에 원문과 다른 곳은 없다(`diff`로 기계 대조하여 확인,
2026-08-05).

| # | 위치 | 내용 | 성격 |
|---|------|------|------|
| 1 | A.6.3 `enum` 행 값 형식 | "— 항목은 base가 가질 수 있는 값이어야 한다(아래)" 추가 | 실질 변경(이 갱신의 본체) |
| 2 | A.6.3 첫 문단 | "어휘의 추가·삭제는 **이 RFC**의 개정 사항이지" → "**RFC-0001 계열**의 개정 사항이지" | 참조 정정 — 텍스트가 이 문서로 옮겨오면 "이 RFC"가 RFC-0011을 가리키게 된다. 가리키는 대상은 바뀌지 않는다 |
| 3 | A.7 ⓔ 행 | 충돌 대상에 "같은 문서의 Entity 이름" 추가, 이유 칸에 이름공간 공유 근거 추가 | 실질 변경(이 갱신의 본체) |
| 4 | A.7 마지막 문단 | "다만 v0.1 참조 구현에는 **아직 없다** … 구현은 후속 태스크의 몫이며" → 구현 완료 사실로 교체 | 사실 정정 — 원문은 2026-08-04 시점의 실측이었고 그 뒤 이슈 #31이 랜딩하며 5종이 모두 구현되었다. 규범(ⓐ-ⓔ의 내용)은 바뀌지 않으며, 거짓이 된 상태 서술만 갱신한다. 그대로 옮기면 새 Accepted RFC가 거짓을 담게 된다 |
| 5 | A.7 끝 | 대소문자 판정 문단 신설 | 명확화 — ⓔ의 "충돌"이 정확한 일치인지 대소문자 무시인지 원문이 말하지 않았다. 실측(`Link`/`link` 은 별개 키)에 따라 정확한 일치로 확정한다 |

## 부록 A.6.3 (치환 후 최종 텍스트)

> 이 절은 RFC-0001 부록 A.6.3을 대체한다. RFC-0007 §2.2 규칙 3에 따라 효력 있는
> 계약은 "RFC-0001 본문에서 A.6.3을 아래 텍스트로 치환한 것"이다.

**A.6.3 facet 어휘.** **정확히 6종의 닫힌 열거**이며, 본문이 허용한 강화
방향("범위·패턴·열거·길이 추가") 4계열의 전개다. 어휘의 추가·삭제는 RFC-0001
계열의 개정 사항이지 문법의 확장이 아니다.

| facet | 값 형식 | 적용 base 범주 |
|-------|--------|---------------|
| `minLength` | 정수 ≥ 0 | 텍스트류 |
| `maxLength` | 정수 ≥ 0 | 텍스트류 |
| `pattern` | 문자열(ECMA-262 정규식) | 텍스트류 |
| `min` | 수치 | 수치류 |
| `max` | 수치 | 수치류 |
| `enum` | 배열(문자열 또는 수치), 1개 이상 — 항목은 base가 가질 수 있는 값이어야 한다(아래) | 텍스트류 · 수치류 |

base 18종은 네 범주로 나뉘며 범주가 적용 가능한 facet을 정한다. 개별 타입
예외는 두지 않는다.

| 범주 | base (계 18) | 허용 facet |
|------|-------------|-----------|
| 텍스트류 (9) | UUID, Email, Password, DateTime, Phone, Currency, Html, Markdown, Text | `minLength` `maxLength` `pattern` `enum` |
| 수치류 (2) | Integer, Decimal | `min` `max` `enum` |
| 진리값 (1) | Boolean | 없음 — 2값으로 이미 닫혀 있다 |
| 복합류 (6) | Money, GeoLocation, Address, Image, File, Json | 없음(v0.1) — 내부 필드를 지목할 표기가 없다(Open Questions ⑤) |

**enum 항목과 base의 정합.** `enum` 배열의 각 항목은 그 `base`가 실제로 가질 수
있는 값이어야 한다. 항목은 **표기 형태**로 분류한다 — RFC-0002 어휘의 `Number`는
소수점 표기가 없으면 *정수*, 있으면 *소수*로 읽고(`min`/`max`가 쓰는 것과 같은
변환), 그 밖의 `Word`는 *문자열*로 읽는다. 허용 판정은 다음과 같다:

| base | 허용되는 항목 |
|------|--------------|
| 텍스트류 9종 (UUID, Email, Password, DateTime, Phone, Currency, Html, Markdown, Text) | 문자열만 |
| `Decimal` | 정수 또는 소수 |
| `Integer` | 정수만 — 소수점 표기(`2.0` 포함)는 불가 |
| 진리값 · 복합류 | `enum` 자체가 적용되지 않는다(위 범주 표) |

위반은 컴파일 오류다. 이는 A.7이 구분한 **문서 수준 불변식**에 속한다 — JSON
Schema는 `enum` 항목의 타입을 노드 단위로만 볼 뿐 그 항목이 같은 노드의 `base`와
맞는지는 필드 간 상호 의존이므로 표현할 수 없다(A.7 ⓓ와 같은 이유).

**`Integer`가 범주보다 좁은 이유.** `min`/`max`는 **경계**이므로 `Integer`에
`min 1.5` 를 주어도 2 이상의 모든 정수를 여전히 허용한다 — 죽은 제약이 아니다.
`enum`은 **허용 값의 열거**이므로 base가 가질 수 없는 항목은 어떤 값도 만족시킬
수 없는 죽은 항목이다. 항목의 분류 방식은 `min`/`max`와 동일하게 두고(표기 형태),
허용 판정만 facet의 의미에 맞춘다.

## 부록 A.7 (치환 후 최종 텍스트)

> 이 절은 RFC-0001 부록 A.7을 대체한다. RFC-0007 §2.2 규칙 3에 따라 효력 있는
> 계약은 "RFC-0001 본문에서 A.7을 아래 텍스트로 치환한 것"이다.

**A.7 스키마 검증의 범위.** JSON Schema는 노드 단위 구조·타입(필수 필드,
kind별 허용 필드, enum 값, id 형식)만 검증한다. 문서 수준 불변식 — id 유일성,
dangling 참조 금지(구조 규칙 6), 소유 유일(규칙 2), 비순환(규칙 4), kind별
children 허용 종별 — 은 스키마 표현 범위 밖이며, 컴파일 파이프라인의 검증
패스(RFC-0004 계열)가 소유한다. `scripts/validate_ir.py`는 스키마 검증까지만
수행한다.

A.6이 추가한 불변식 5종도 같은 구분을 따른다. 스키마는 `Refinement` 노드의
구조(필수 필드, `base`가 18종 안인지, facet 키가 어휘 안인지, 값의 타입,
`name`의 PascalCase 형식)까지 검증하고, 아래는 **패스가 소유한다**:

| # | 불변식 | 스키마가 못 잡는 이유 |
|---|--------|---------------------|
| ⓐ | `fields[].type`의 이름이 A.6.1 순서로 해소된다 | 문서 전역의 `Refinement.name` 집합을 봐야 한다 |
| ⓑ | `facets`가 1개 이상이다 | 스키마가 쓰는 키워드 집합 밖(`minProperties` 미사용) |
| ⓒ | `enum` 배열이 1항목 이상이다 | 같음(`minItems` 미사용) |
| ⓓ | 각 facet이 `base`의 범주에 허용된다(A.6.3 표) | 필드 간 상호 의존이다 |
| ⓔ | `name`이 18종·preset·**같은 문서의 Entity 이름**·타 `Refinement`와 충돌하지 않는다 | 문서 전역 유일성이다. Entity와 Refinement는 `components/schemas` 한 이름공간을 공유하므로(A.6.6·RFC-0004) 같은 이름은 한쪽이 다른 쪽을 덮어쓴다 |

**이 5종은 규범적 요구다 — 패스는 위반 시 오류를 일으켜야 한다.** v0.1 참조
구현은 이슈 #31의 랜딩(2026-08-04)으로 5종을 모두 갖추었다: ⓐ는 해소되지 않는
타입 이름을, ⓑ·ⓒ·ⓓ는 facet의 개수·항목 수·범주 적용을, ⓔ는 이름 충돌을 각각
`LowerError`로 거부한다. ⓔ의 Entity 이름 확장은 이 갱신과 함께 구현된다.

**충돌 판정은 이름의 정확한 일치**다(대소문자 구별). `Link` 와 `link` 은 서로
다른 `components/schemas` 키가 되어 어느 쪽도 덮어쓰지 않으므로 충돌이 아니다
(2026-08-05 실측).

## 검증

이 갱신은 다음이 성립할 때 충족된다. 각 항목은 반증 가능하다.

| # | 소스 | 기대 |
|---|------|------|
| 1 | `refine Kind of Text` + `enum draft published` | 허용 — `["draft", "published"]` |
| 2 | `refine Kind of Text` + `enum draft 1 2.5` | **거부** (컴파일 오류) |
| 3 | `refine Kind of Text` + `enum 1` | **거부** |
| 4 | `refine Price of Decimal` + `enum 1 2.5` | 허용 — `[1, 2.5]` (정수·소수 혼재 가능) |
| 5 | `refine Score of Integer` + `enum 1 2.5` | **거부** — `2.5` 는 소수 |
| 6 | `refine Score of Integer` + `enum 2.0` | **거부** — `2.0` 은 소수 표기 |
| 7 | `refine Score of Integer` + `enum 1 2 3` | 허용 |

2·3·5·6의 오류는 위반한 항목과 base를 함께 지목해야 한다 — 어떤 항목이 왜
불가능한지 알 수 없는 진단은 이 갱신의 목적을 달성하지 못한다.

이름 충돌(A.7 ⓔ):

| # | 소스 | 기대 |
|---|------|------|
| 8 | `refine Link of Text` + `entity Link` | **거부** (컴파일 오류) — 선언 순서와 무관하다 |
| 9 | `refine Link of Text` + `entity link` | 허용 — 대소문자가 다르면 별개 키다 |
| 10 | `refine Linkish of Text` + `entity Link` | 허용 — 단순히 비슷한 이름은 충돌이 아니다 |

8의 오류는 컴파일 단계에서 나야 한다. 생성기의 `OpenApiError` 가드는 제거하지
않는다 — `lower` 를 거치지 않고 만들어진 IR 문서(에이전트가 직접 생성했거나
외부 도구가 쓴 `.lir.json`)에 대한 심층 방어로 남는다.

참조 구현의 대응 위치는 `impl/lnpl/lower.py`(facet 파싱과 `taken` 집합)이며,
검증은 `impl/tests/test_lower.py`가 위 10행을,
`impl/tests/test_openapi.py`가 생성기 가드를 각각 고정한다.
